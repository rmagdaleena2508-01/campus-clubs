1. The problem

SRM has many clubs, and most of them sit under the engineering departments. Every club runs on the same tools: Google Forms and WhatsApp groups. These tools do not talk to each other, so a lot gets lost.

A story from today

Riya is in second year. She wants to join the Robotics Club.

  1. She sees a Google Form link in a WhatsApp group. She fills it in. She never hears back.
  2. A month later, a friend tells her about a robotics contest. She was not in the right WhatsApp group, so she almost missed it.
  3. On the day, the room changes. The message gets lost in 200 other messages. She goes to the wrong room.
  4. She takes part and her team comes second. The result is never posted anywhere.
  5. Later, a company asks for proof. She has nothing to show.

What goes wrong, step by step

StepTool used todayWhat goes wrong
Finding new membersGoogle FormEvery club makes its own form with its own rules. Only the leader sees the answers. People who apply never hear back.
Telling people about an eventWhatsApp groupMessages get buried. People outside the group never know. Room or time changes get missed.
Signing up for an eventAnother Google FormNo seat limit. Same person signs up twice. No way to check students from other colleges.
AttendancePaper or a sheetSlow and easy to fake. Often never saved.
ResultsNowhereWinners are said out loud on stage and then forgotten.
Proof you took partHand-made certificate, if anyEasy to fake. Nobody can check if it is real.
The root problem: each step lives in a different tool, so nothing flows from one step to the next. The data breaks between join, sign up, attend, result and proof.

2. Why I am solving it

  • I live this problem. I am an SRM student. I see these forms and WhatsApp groups every week, and I know how the clubs really work.
  • It helps many people. Thousands of students, and every club leader who loses a whole weekend to forms and sheets after each event.
  • It gives students real proof. A profile with results, certificates and badges that anyone can check.
  • I want to learn full-stack engineering for real. Frontend, backend, database, security and deploying, all on a product people actually use.
  • It has been done before, and it worked. A team built a similar project called CampusConnect and won a Best Project award. I studied their code. I will keep what worked and fix the weak spots I found.

What I learned from CampusConnect

Keep (it worked well)Fix (weak spots I found in their code)
  • Clean layers: routes, then logic, then database
  • Club leader is a membership, not a login type
  • Certificates with a QR code that links to a public check page
  • The AI only phrases answers. Code picks the clubs, so the AI cannot make them up.
  • Anyone could sign up as an admin. Here, only I can make an owner, from the command line.
  • Anyone could type a fake college email. Here, SRM users must sign in with their real Google account.
  • Login tokens lasted 28 days in browser storage. Here, sessions sit in a safe cookie that page code can't read.
  • Certificate numbers could be guessed. Here, they are long random codes.
  • Attendance was ticked by hand. Here, it is a QR scan.

4. What it must do

A. Hiring club members (replaces Google Forms)

  • The Club Admin sets the rules once: open and close dates, who can apply (year, department), how many seats, and the questions.
  • Every application goes into one queue.
  • Each person moves through steps: Applied, Shortlisted, Interview, Selected or Not selected.
  • The student sees their step live and gets told when it changes.
  • Picking someone as "Selected" makes them a member right away.

B. Events (replaces WhatsApp)

  • Each event has its own page: room, time, map link, seats left and live status.
  • Changes like "Room moved to Hall B" or "Starting now" reach everyone signed up by email and phone notification.
  • SRM students are confirmed right away. Outside guests wait for a yes from the event team.
  • The app never lets more people in than there are seats.

C. One flow: sign up, check in, result, certificate, badge

  • Check-in is a QR scan at the door. The code changes every 30 seconds, so a screenshot shared on WhatsApp will not work.
  • Results go on the event page and stay there forever.
  • Certificates are made by the app, with a QR code anyone can scan to check they are real.

D. One club list, one profile, real proof

  • A list of every club. You can filter it by campus, department and type. Your own campus shows first.
  • Every student gets a public page at /u/their-name with clubs, events, results, certificates and badges.

E. Badges, like GitHub

  • The app gives badges by itself, based on what really happened. Examples: First Event, Hackathon x3, Winner, Core Member.
  • Badges have levels like GitHub's (x2, x3, x4).
  • Each badge has a public check link.
  • A small badge card can be added to a GitHub README or a LinkedIn profile.
Not in version 1: paid events, chat between students, a phone app from the app store (the website works well on phones) and AI features. The AI club finder comes after the main flow works.

5. How I will build it (my approach)

  1. Start from the problem, not the code. Every feature must fix a step in the "what goes wrong" table.
  2. Build thin slices. Each phase works from start to end: backend, frontend, tests and a live link. No half-built parts sitting around.
  3. Ship every phase. Every phase ends with something live that people can click.
  4. Safe by default. The database itself blocks bad data, like a winner who never checked in. Every permission goes through one check function.
  5. Test the rules. Each important rule gets a test. Tests run by themselves on every change.
  6. Real users early. Start with 3 clubs at one campus (KTR), learn, then open to all.
  7. Write it down. The docs, the database file and this PRD live in the GitHub repo and are updated with each phase.

8. Keeping it safe

DangerWhat we do
Someone pretends to be an SRM studentSRM users sign in only with Google. The server checks the account belongs to srmist.edu.in. A personal Gmail is turned away.
Someone makes themselves an adminNo sign-up form can make an owner. Only I can, from the command line. Club Admins come only from approved clubs.
Someone steals a loginThe login is a random code in a locked cookie that page code can't read. You can log out of all devices.
A bad site tricks your browser into a clickEvery change needs a secret token that only our own website knows (CSRF protection).
Someone guesses email codesCodes expire in 10 minutes, die after 5 wrong tries, and requests are limited.
A friend shares a check-in QR on WhatsAppThe QR code changes every 30 seconds and works only once.
Someone fakes a certificateEvery certificate has a long random code and a public check page.
A leader does something wrongEvery admin, core and owner action is written to an audit log: who, what, before, after and when.
Bad data gets inEvery input is checked. The database also blocks bad data on its own, like signing up twice or a winner who never came.
Private data leaksCollect only what we need. Students can delete their account. This follows India's DPDP Act 2023.

9. Handling many people at once

The hard moment is not "many users in total". It is a rush: a hackathon opens 300 seats, and 3,000 people click in the same minute.

  1. No overbooking. A seat is taken in one database step that only works if a seat is left. People can't sign up twice.
  2. Many copies of the server. The server keeps nothing in its own memory. Logins sit in Redis, so 1 copy or 20 copies all work the same.
  3. Slow work goes to the job line. The leader clicks "Publish results" and gets an answer at once. Certificates and emails come a minute later.
  4. Public pages are saved near users (CDN). The club list, results and profiles load fast and barely touch the server.
  5. Database care. Indexes for common searches, page-by-page lists, and a pool of open connections.
  6. Practice the rush. Before the first big event, a test tool (k6) fakes 3,000 sign-ups in 60 seconds.

10. My three jobs: frontend, backend, deploy

I do all three jobs myself. Writing them down keeps each job clear, and shows what to hand over if more people join later.

Frontend Engineer: "what people see and click"

  • Builds every page in Next.js: sign in, club list, club page, hiring form, queue, events, scanner, profile.
  • Makes it work well on phones first, since most students use phones.
  • Makes it easy for everyone to use (screen readers, keyboard, clear colors).
  • Shows clear messages when something goes wrong, and loading states while waiting.
  • Uses the API types made from the backend, so the two never disagree.
  • Writes Vitest tests for parts and Playwright tests for full click paths.

Backend Engineer: "the rules and the data"

  • Designs the database and keeps db/schema.sql up to date.
  • Builds the API endpoints in FastAPI.
  • Owns sign-in, sessions and the can() permission check.
  • Builds the background jobs: certificates, emails, badges.
  • Writes a test for every rule (seat limits, who can do what, and so on).
  • Keeps the API docs correct.

Developer / DevOps Engineer: "getting it live and keeping it up"

  • Sets up GitHub: branches, pull requests, issue board, GitHub Actions.
  • Deploys the web app to Vercel, the API to Render, and sets up Neon, Upstash and R2.
  • Keeps secrets (keys and passwords) out of the code, in each host's secret settings.
  • Sets up Sentry for errors, daily database backups and uptime checks.
  • Runs the rush test before big events.
  • Publishes the project page and docs on GitHub Pages.

12. How every release ships

  1. Small branch. One feature per branch, for example feat/event-signup.
  2. Pull request. Explain what changed and why, in plain words.
  3. Auto tests. GitHub Actions runs every backend and frontend test. Red means stop.
  4. Preview link. Vercel makes a preview link. I click through the change on a phone and a laptop.
  5. Merge. Merging to main deploys the web app (Vercel) and the API (Render) by itself.
  6. Database changes. Alembic runs the change before the new API starts. Take a backup first.
  7. Check. Look at Sentry and the health check for 15 minutes after each release.
  8. Update the docs. Update the README status table and this PRD on GitHub Pages.
